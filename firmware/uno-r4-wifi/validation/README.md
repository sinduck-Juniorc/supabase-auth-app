# R4 구현 검증 기록

UNO R4 WiFi 한 대로 시작할 펌웨어를 구현했다. 실제 검증 범위는 아래 Linux 클라우드의 크로스 컴파일과 호스트 검사다. 사용자 Windows PC의 보드에는 접근할 수 없어 업로드·BLE 수신·전류를 측정하지 않았다.

## 빌드 결과

| 설정 | 노드 ID | Flash [bytes] | 정적 RAM [bytes] | 컴파일 |
|---|---:|---:|---:|---|
| diagnostic | 1 | 87492 | 10048 | 통과 |
| donor | 1 | 87496 | 10052 | 통과 |
| relay | 2 | 87496 | 10052 | 통과 |
| seeker | 3 | 87496 | 10052 | 통과 |

Flash/RAM은 RA4M1 스케치에 대한 컴파일러 집계다. ESP32-S3의 메모리·실행 중 최고 RAM·보드 전력값을 뜻하지 않는다. SDK 내부 경고는 남아 있으며 스케치에서 발생한 경고는 없었다. 최종 로컬 컴파일 로그는 compile-role0.txt~compile-role3.txt에 보존했다. 초기 클린 빌드의 SDK 경고 목록은 initial-sdk-warnings.txt에 있으며 캐시 재사용 빌드에서는 해당 경고가 재출력되지 않을 수 있다. 요약과 바이너리 SHA256은 checks.json에 보존했다.

## 검사와 한계

- CRC-16 표준 벡터, 26바이트 직렬화, 잘못된 입력/버전/CRC, TTL/홉 제한, 중복, millis 순환, 논리적 2홉 검사 통과. 논리적 2홉은 실물 RF 시험이 아니다.
- Python 3.11 로그 파서 검사 2개 통과. 잘못된 JSON·비유한/과대 숫자·결측·잘못된 역할을 처리했다.
- 없는 포트를 열면 오류로 종료하고 원자료를 생성하지 않았다. 이 실패 경로 시험은 보유 R4의 COM 포트 검사가 아니다.
- Arduino CLI 1.5.1 공식 배포물의 SHA256을 공식 체크섬과 대조했다. core 1.6.0, ArduinoBLE 2.1.0, Arduino_SpiNINA 0.0.2를 고정했다.
- 실제 RF의 채널/스캔창·패킷 수명·3노드 중계·전력·GNSS·TTFF는 미검증이다. 고정 진단/중계 기준선만 구현했고 제타·체비쇼프/RL은 R4에 이식하지 않았다.

## 기존 50노드 결과와 구분

아래 수치는 이전에 실행한 Linux EPYC/Python 3.11, 50노드·90초·시나리오별 30개 평가 시드의 평균이다. 이번 R4 작업에서 새로 실행하거나 R4로 측정한 수치가 아니다. 에너지는 당시의 미실측 전류 가정에 따른 모형 추정이다.

| 시나리오 | 기준선 | 에너지 J: 기준선→combined | 성공률 %: 기준선→combined | p95 s: 기준선→combined |
|---|---|---:|---:|---:|
| 등산로 희소 | fixed | 78.38 → 59.55 | 89.61 → 69.97 | 8.09 → 8.15 |
| 도심 차폐 | random | 84.98 → 63.23 | 92.42 → 72.75 | 6.89 → 8.14 |
| 밀집 군집 | fixed | 84.99 → 58.95 | 94.96 → 83.02 | 5.70 → 7.82 |

이전 통합 정책은 성공률 감소가 허용치 2%p를 넘어 초기 성공 기준을 만족하지 못했다. R4 사용으로 이 결과가 개선됐다고 주장할 수 없다. 기존 전체 원자료·통계·그림은 원래 ZetaMesh50 연구 결과 묶음에 남아 있다.

## 다음 실제 확인

1. Windows Arduino IDE에서 업로드하고 115200 baud의 ble_ready/상태 로그를 확인한다.
2. 휴대폰 BLE 검색 앱으로 광고와 ZM 제조사 데이터를 확인한다.
3. 실제 COM 포트에서 60초 로그를 모아 코드 버전·보드/펌웨어 조건과 함께 보존한다.
4. 다른 노드를 확보하면 같은 전력/PHY에서 직접 링크 실패와 2홉 수신을 분리해 시험한다.
5. R4의 실제 전력·타이밍을 측정해 모형을 보정한 뒤 수신기 지원을 확인하고 GNSS 주입을 별도로 시험한다.
