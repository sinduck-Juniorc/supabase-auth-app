# ZetaMesh — 50개 노드 실증을 위한 에이전트 실행 명세서

- 버전: 1.0
- 작성일: 2026-11-08
- 연구용 PC: AMD Ryzen 5 5600X (6C/12T), RAM 32 GB, NVIDIA GTX 960, Windows
- 제약: 신규 GPU·PC 구매 없음. 학습과 실험은 CPU 중심, Windows 네이티브 Python 우선. WSL2는 선택 사항.
- 범위: **50개 가상 BLE 노드**의 네트워크 시뮬레이션과, 별도 **실물 ESP32-C3 3개 노드**의 교차 검증. 물리 노드 50대 제작을 요구하지 않는다.
- 이 문서는 기존 `ZetaMesh_Ryzen5600X_연구환경_설계서.md`의 50노드 실험 목표 및 실행 기준을 구체화·우선한다. 기존 문서 없이도 연구를 시작할 수 있어야 한다.

## 0. 에이전트 지시: 연구를 실제 수행할 것

요구사항을 계획으로만 끝내지 말 것. 코드, 실행 명령, 단위 테스트, 반복 실행, 실험 결과 CSV/그림/한국어 보고서를 산출한다. 사용 가능한 컴퓨터에서 의존성을 설치할 수 없거나 하드웨어가 없는 경우, **실행한 결과와 실행하지 못한 항목을 명확하게 분리**한다. 데이터나 측정 결과를 만들어 내지 말 것.

## 1. 검증할 연구 가설

**주가설 H1:** 50노드 등산로·도심·밀집 환경에서 `[체비쇼프 경량 품질 추정 → 제타 가중 donor/relay 후보 선택 → 적응형 BLE 스캔·광고·중계 스케줄]`이 고정 주기/무작위 백오프 등의 기준선보다, 유효 보조정보 수신률을 유지하면서 네트워크 전체 에너지(J)를 줄일 수 있다.

**부가설 H2:** 체비쇼프 다항식 근사는 더 복잡한 teacher 모델 또는 실측 피팅 함수를 충분히 잘 근사하면서 ESP32-C3에서 CPU 소요 시간과 코드/메모리 비용을 줄일 수 있다.

**부가설 H3:** 제타 가중 정책은 단순 그리디 donor 선택과 비교해 정보 신선도, 탐색 지연, 에너지 간의 트레이드오프를 개선한다.

**금지할 과도한 주장:** 수학적인 제타/체비쇼프 구조만으로 BLE 단일 홉 RF 거리가 늘어난다고 주장하지 말 것. 메쉬 범위 확장은 **중계 효과**, 단일 홉 거리 증가는 PHY/송신전력/수신감도/안테나/환경 효과로 분리한다. A-GNSS 보조정보를 수신·저장하는 것과 **수신기 하드웨어에 주입하여 TTFF가 단축되는 것**은 분리한다.

## 2. 시스템 아키텍처 — 화면의 4단 구조를 구현

```text
┌─────────────────────────────────────────────────┐
│ GNSS · BLE · 배터리 상태 수집                     │
│ RSSI, 수신 성공률, 후보 정보 연령, 정확도, 잔량 등 │
└────────────────────┬────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────────┐
│ 체비쇼프 기반 경량 품질 추정                      │
│ 특징량 정규화 → 적합된 저차 다항식 → 품질 점수 Q │
└────────────────────┬────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────────┐
│ 제타형 가중 후보 선택                             │
│ 정렬된 후보 r=1..K, P(r)=r^(-s) / Σ k^(-s)       │
│ (상태 기반 s 조절·최소 탐색확률 확보)            │
└────────────────────┬────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────────┐
│ BLE 탐색 · 광고 · 중계 · 절전 스케줄러             │
│ 스캔 윈도우/간격, 백오프, 릴레이 TTL, 만료 처리   │
└─────────────────────────────────────────────────┘
```

**중요 구현 제약:** 미발견 이웃은 RSSI·GNSS 상태를 알 수 없다. 따라서 첫 발견에는 공통 BLE 광고·스캔 기준 정책을 사용하고, 제타 가중 donor 선택은 발견된 후보 또는 유효한 캐시 내에서만 적용한다. 후보가 0개면 안전한 탐색 폴백을 사용한다. 확률 가중치는 RF 신호 세기나 채널을 직접 증폭하지 않는다.

## 3. 데이터·메시지 모델

각 노드: `node_id, role, pos_xy_m, velocity_mps, battery_soc, scan_interval_ms, scan_window_ms, adv_interval_ms, tx_power, neighbor_cache, relay_budget, sleep_state`.

각 후보: `last_seen_ms, rssi_dbm, estimated_p_rx, gnss_quality, fix_age_s, info_age_s, expiration_s, hops, remaining_battery`.

전송 응용 메시지: `version, packet_id, source_id, message_type, created_at, expires_at, hop_count, max_hops, quality_code, payload_bytes, integrity_tag`.

- 버전, TTL/만료, 중복 방지, 정수 단위, 결측치, 악의적/오류 데이터의 무시 규칙 정의.
- 처음에는 **가상 GNSS 보조 패킷** 사용. 실제 GNSS 수신기에 지원되는 보조정보 주입이 검증되기 전에는 `A-GNSS TTFF 절감`을 실증했다고 쓰지 말 것.
- 개인정보 보호: 다른 단말의 정확한 위치를 기본적으로 저장하지 말고 필요 최소 데이터와 명시적 동의 원칙을 설계한다.

## 4. 시뮬레이터 구축: 50개 노드로 고정

### 4.1 모듈

- `simulator/topologies.py`: 50개 노드 좌표·이동 모델. 세 환경 아래.
- `simulator/radio.py`: 최대 범위, 거리 감쇠, 장애물/페이딩, 링크 수신 성공 확률. 3개 BLE 레거시 광고 채널(37, 38, 39)의 충돌 가능성/수신창 중첩을 최소한 이벤트 수준으로 반영하고 **무엇을 생략했는지 기술**.
- `simulator/events.py`: 광고, 스캔 윈도우, 패킷 충돌, 수신, 중계, 절전, 만료.
- `simulator/energy.py`: 모델별 TX·RX·scan·idle·sleep·CPU 및 GNSS 활성 시간, `E=Σ P_state Δt` [J]. 전류·전압 값은 보드 실측 전까지 **가정값/민감도 변수**로 명시.
- `simulator/network.py`: 후보 발견, 중복 억제, 메쉬 TTL, 폴백.
- `simulator/metrics.py`: 시드별 에너지, 성공률, p50/p95 발견 지연, 유효 패킷 수령시간, 중계 횟수/부하, 정보 만료율.

### 4.2 50노드 고정 시나리오 (각각 50개)

A. **등산로 희소 노드**: 길을 따른 선형·군집 배치, 일부 구간 단절, 낮은 Donor 밀도, 걷는 이동 속도.

B. **도심 차폐 노드**: 건물 차폐/비가시선 확률, 광고 간섭·음영 지역, 이동 속도 다양화.

C. **밀집 군집 노드**: 협소한 구역에 50개 노드, 광고 중첩·중복 중계 증가.

각 시나리오에서 donor 비율(예: 10%, 20%), 요청 빈도, 정보 만료시간, 링크 열화 정도를 변화시키되 초기에는 조합 폭증을 피할 것. **표본 시나리오 및 파라미터를 YAML 파일로 고정하고 매 실행에 기록**한다.

### 4.3 반복/측정

- 먼저 3노드 → 10노드 동작 테스트. 그다음 평가 규모를 **50개 노드**로 고정.
- 시나리오별 **독립 난수 시드 최소 30회**. 학습/튜닝 데이터와 평가 시드 분리.
- 동일 시드·토폴로지·초기 상태/트래픽으로 모든 정책 비교(가능하면 paired 비교).
- 각 실험의 시뮬레이션 시간, 이벤트 개수, CPU 벽시계 시간, 최고 RAM 기록.
- 다중 프로세스 4개로 시작; PC가 원활한 경우 6개 비교. RAM 초깃값 상한 권고 24GB. GPU 학습은 기본 비활성.

## 5. 반드시 구현할 기준선 및 제거 실험(ablation)

1. `fixed`: 고정 광고/스캔 주기, 기본 relay.
2. `random`: 고정 정책 + 의사난수 jitter/backoff.
3. `greedy`: 발견된 donor 중 품질 점수가 최고인 후보 선택.
4. `zeta_only`: 간단한 점수 함수 + 순위 가중 `P(r)∝r^{-s}`.
5. `cheb_only`: 체비쇼프 품질 점수 + 그리디 또는 기준 선택(제타 없음).
6. `combined`: 체비쇼프 점수 + 제타 선택 + 적응 스케줄.
7. `teacher_rl` (2차 목표): PPO의 작은 MLP 정책. RL 없이도 1~6을 완성할 것.
8. `cheb_distilled` (2차 목표): RL/회귀 teacher의 결정 함수를 저차 체비쇼프 근사로 증류.

모든 정책의 스캔·광고 가능 범위, 전달 요구사항, PHY, 송신전력, max_hops는 동일. `combined`와 `zeta_only`뿐 아니라 단순 LUT/임계값 정책을 비교해 **수학적 이름 자체가 아니라 실제 성능**을 검증한다.

## 6. 체비쇼프 모델 요구사항

- 제공됐던 `ChebyshevT3Codec`의 `T3(x)=4x³−3x`는 신호를 접는 **양자화 코덱**이다. 여기서 쓰는 것은 그 코드의 직접 적용이 아니라 **학습된 품질/정책 함수의 체비쇼프 기저 근사**임을 명시할 것.
- 입력 `RSSI, battery, age, hops, p_rx ...`는 정규화하고 결측/범위 초과를 처리한다.
- 다변수 점수 함수는 1D 체비쇼프만으로 대체하지 말고 가산형 성분·상호작용항·작은 LUT·작은 MLP와 비교한다.
- 계수는 PC에서 학습/최적화; ESP32에서는 Clenshaw 또는 적절한 다항식 평가 방식으로 추론.
- 차수 3, 5, 7과 LUT/선형/결정트리/MLP 비교. 테스트 오차 MAE/RMSE/최대값, 실행시간, RAM/Flash, 추론 에너지 검증.
- 샘플 코드의 `decode_newton()` 경계부 취약성과 양자화·전송 오버헤드를 수정 없이 생산용으로 쓰지 말 것. 위치 좌표는 정수 좌표/차분 인코딩을 별도 평가.

## 7. 평가 지표와 사전 등록 성공 기준

**1차 평가 단위는 노드당이 아닌 네트워크 전체 에너지 합계[J]**이다. Donor/Relay/Seeker 별 에너지도 별도 표로 낸다.

- **Primary**: 동일 QoS 조건에서 `combined`의 50노드 네트워크 총에너지와 `fixed`, `random`, `greedy` 비교.
- QoS: 유효 패킷 데드라인 내 수신률, p95 발견·전달 지연, 만료율, 이웃 발견 실패율.
- 목표 기준(사전 지정, 보장 성능 아님): 기존 최고 기준선 대비 **전체 에너지 10% 이상 감소**, 데드라인 내 성공률 **절대 2%p 이하 감소**, p95 전달 지연 **5% 이하 악화**. 이 세 조건을 모두 만족할 때만 "초기 성공"이라 부른다.
- 통계: 각 시나리오 30개 이상의 시드에서 paired 차이와 95% 신뢰구간. 기준 충족의 불확실성도 보고한다. 결과가 실패하면 원인과 조건을 공개.
- `combined`가 `cheb_only`나 `zeta_only`보다 낫지 않으면 통합 복잡도 증가를 정당화하지 말 것.
- 체비쇼프 경량화 결과는 CPU의 모델 추론 비용과 전체 BLE/GNSS 에너지 절감을 **별개의 지표**로 제시.
- 실측 전 모델 가정의 전력 개선 숫자는 "시뮬레이션 기반 추정"으로 표기.

## 8. 실행·설치 가이드 (5600X / Windows)

1. Python 3.11(64-bit), Git, VS Code 설치.
2. 프로젝트 폴더에서 `py -3.11 -m venv .venv`, `.venv\Scripts\python.exe -m pip install numpy scipy pandas matplotlib simpy scikit-learn optuna pytest psutil gymnasium`.
3. RL은 2차 단계에서 CPU PyTorch 및 Stable-Baselines3 설치(`device='cpu'`). GTX 960 CUDA 대응은 우선순위 밖.
4. 모든 벤치마크·그림은 시드, 조건, 코드 버전(commit), PC 사용률·시간을 함께 기록.
5. `configs/50nodes_*.yaml`과 `python -m scripts.run_experiment --config ... --policy ... --seeds 30` 식으로 재현 가능한 CLI 구현. 실제 인자와 이름은 README에 확정·명시.
6. 결과는 `outputs/<timestamp-or-run-id>/`에 저장하되 실험 코드의 버전 정보를 함께 남긴다.

## 9. 하드웨어 검증: ESP32-C3 3대 (선택적 2차 단계)

- A(Donor) / B(Relay) / C(Seeker), A→C 직접 불가, A→B→C 유효 수신 증명.
- BLE 스캔/광고(멀티홉) 로직과 통신 성공·지연 로그부터 구현. Bluetooth Mesh 표준 구현과 자체 BLE 중계 프로토콜을 구분해 표기.
- ESP-IDF 사용 권장; Arduino IDE는 기초 통신·센서 검증에 사용 가능.
- `RSSI, p_rx, scan current, TX current, idle/sleep current` 실제 수치 측정하여 시뮬레이터 보정.
- INA219 평균 전류 측정만으로 아주 짧은 무선 피크나 세밀한 전력 분해를 검증했다고 주장하지 말 것.
- 우선은 가상의 GNSS 패킷을 중계. 실제 A-GNSS 보조정보 수신기 주입과 TTFF는 별도 과제.

- [ ] 기능이 비슷한 단순 정책보다 통합 알고리즘이 유의미하게 나은지 결론을 낸다.

## 11. 우선순위 및 중단 조건

- 1순위: 실측/이론적으로 일관된 50노드 시뮬레이터와 기준선.
- 2순위: 제타 가중 선택, 체비쇼프 정책 근사, 교차 비교.
- 3순위: 작은 RL teacher 및 증류.
- 4순위: ESP32-C3 3대 실측과 GNSS 보조정보 연계.
- 성능 비교가 기준선을 못 넘으면 RL이나 수학적 복잡도를 늘리기 전에 에너지 모델·스케줄링·정보 TTL을 점검한다.
- 한 번의 실행이 너무 오래 걸리면 이벤트 로그 경량화, 프로파일링, 단순 채널 모형, 병렬 시드 실행 순서로 최적화한다. **평가 노드 50개는 유지한다.**
