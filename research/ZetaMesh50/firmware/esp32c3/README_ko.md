# ESP32-C3 3대 검증 준비 — 미실행

이 폴더에는 실행 가능한 펌웨어가 없다. 현재 환경에 ESP32-C3·GNSS·전류 계측기가 연결되지 않아 펌웨어 빌드/플래시/실측을 수행하지 않았다. 작업 범위의 별도 2차 단계로 남긴다.

1. 보유 3대를 A=Donor / B=Relay / C=Seeker로 정한다. Windows VS Code의 공식 ESP-IDF 도구를 사용하며 BLE 기능은 실제 보드/SDK 버전에 맞춰 고정한다.
2. 광고 메타데이터와 가상 GNSS 패킷의 실제 바이너리 인코딩을 설계한다. 31바이트 legacy 광고에 들어가는지 확인하고 초과하면 프레임 수·전송 시간·단편화/조립·중복 억제를 함께 보정한다. 논리 JSON 객체를 그대로 31바이트 전송했다고 가정하지 않는다.
3. ID/버전/정수 밀리초 시각/최대 홉/만료/체크섬을 적용하고 시간 wrap-around와 시각 동기화 오차를 시험한다. 위변조 방어가 필요하면 별도의 인증 태그와 그 전송/CPU 비용을 정의한다.
4. 동일 PHY·송신전력에서 A→C 직접 수신 불가를 확인한다. 그다음 A→B→C의 동일 packet ID와 hop=2 수신을 로그로 증명한다. 이는 중계 범위 확장이며 단일 홉 RF 거리 증가가 아니다.
5. 시리얼 로그에 역할, ID, version, packet ID, 생성/수신/중계 시각, 채널, RSSI, hop, 만료 사유를 기록한다. 기본 로그에 정확한 위치나 개인 정보는 포함하지 않는다. 시간 동기화 정확도를 함께 측정해 단방향 지연 오차를 보고한다.
6. 사용 가능한 계측기로 TX/RX/scan/idle/sleep·CPU·GNSS의 평균 시간/전류를 보정한다. INA219 평균값만으로 무선 피크를 분해했다고 쓰지 않는다. 장비가 없으면 미측정으로 남긴다.
7. 같은 입력을 사용해 Clenshaw·LUT·단순 선형 C 구현의 출력 오차·주기 수·코드/계수 Flash·스택·증분 에너지를 비교한다. PC Python 추론 시간은 MCU 측정 대신 사용하지 않는다.
8. 수신기가 지원하는 실제 보조정보 주입 API/포맷을 확인한 뒤 GNSS TTFF를 별도 연구한다. 그전에는 가상 패킷 전달로만 표현한다.

이 계획은 자체 BLE 광고 중계 프로토콜용이다. Bluetooth Mesh 표준 스택 구현·인증·상호운용성을 입증하지 않는다.
